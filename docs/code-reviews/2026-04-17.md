## Highest-severity issue: combo decays twice per frame

`gameLoop._runSystems` calls `_tickPlayer` and then `_tickScoring` each frame:

```ts
// src/scenes/gameLoop.ts:380
this._tickPlayer(dilatedDt, input);   // → updatePlayer() decays comboLevel
this._tickAudio();
this._tickScoring(dilatedDt);         // → updateScoring() decays comboLevel AGAIN
```

Both paths called `applyComboDecay`:

- `src/gameplay/player/playerUpdate.ts:131` — in the `else (not drifting)` branch.
- `src/gameplay/scoring.ts:56` — in the `else (not drifting)` branch.

`_tickScoring` also syncs `scoringState.comboLevel ← playerState.comboLevel` before calling `updateScoring`, then writes back, so the player's combo ate two decays per frame. With the default rate that's 4.0/s instead of 2.0/s; with the `comboMaster` upgrade it's 2.0/s instead of 1.0/s. The original single-decay site is `arena-drifter/entities.js:210-211` — there is no equivalent decay in `game.js`.

Why the unit tests missed it: `scoring.test.ts` exercises `updateScoring` in isolation, so each call applied one decay. The bug only surfaces when the full pipeline runs.

### Gameplay impact

- Combo window halved across the whole game.
- Drift combo multiplier drops to 1× far earlier than intended, cutting drift scoring.
- Near-miss streaks lose their combo boost faster.
- The `comboMaster` upgrade is silently nerfed (now equivalent to the base rate).
- Combo-driven upgrades like `comboHeal` fire less often at high thresholds.

## Fix

Branch: **`fix/double-combo-decay`** — commit `67bf59f`.

```
src/gameplay/__tests__/scoring.test.ts | 42 ++++++++++++++++++++++++++++++++++
src/gameplay/player/playerUpdate.ts    |  7 ++++--
2 files changed, 47 insertions(+), 2 deletions(-)
```

- Removed the duplicate `applyComboDecay` call from `playerUpdate.ts`. Scoring is the canonical owner of `comboLevel` (the `ScoringState` interface carries the field and the preexisting decay tests live on `updateScoring`). Dropped the now-unused import and left a comment at the former call site so a future "port-by-the-JS" pass doesn't re-introduce it.
- Added an integration-style test in `scoring.test.ts` that simulates one `_runSystems` frame (`updatePlayer → sync → updateScoring → sync back`) and asserts the combo decays exactly once. Without the fix, the test fails with `comboLevel=0` where `2` is expected (and `2` where `3` is expected for `comboMaster`). With the fix, it passes.

## Other observations (not fixed here)

These were noted during the audit and are lower severity; filing as follow-ups rather than expanding this PR:

- `src/gameplay/enemies/enemyUpdate.ts:70` applies the `distToPlayer > CFG.ENEMY_FAR_DESPAWN_DIST` despawn unconditionally. In `entities.js:523-528` that check is gated by `!onScreen`. At `ENEMY_FAR_DESPAWN_DIST = 1200` with a 1600×900 viewport, an enemy near the opposite edge of the screen from a wall-clamped player can be despawned while still visible. Narrow scenario but a correctness delta.
- `src/gameplay/player/playerState.ts:116-119` applies `thickPlating -= 3` inside `getPlayerRadius()`, which is also used by the renderer. The original only applies that reduction inline at the collision site (`game.js:946`); the player sprite should render at full radius. Cosmetic, but a silent addition.
- `src/gameplay/trail/trailUpdate.ts:131` hard-codes `baseScore = 100 * encircleCount + (encircleCount >= 2 ? 50 * encircleCount : 0)`. Elite kills count as 3 in the original (`world.js:367`). Already marked with a Phase 3 TODO — keep as-is.
- The enemy factory only handles Chaser and Interceptor. This matches the explicit Phase 1 scope (roadmap §1.6) — Drifter/Blocker/Flanker/Bomber/Elite are deferred to Phase 3. Not a bug.
